# 决策记录

只记"选了什么、为什么、否掉了什么"。新决策往下追加。

## D1 重写，不 fork

**决定**：从零写，不复制 BossHunter 的代码。

**为什么**：BossHunter 是 PolyForm Noncommercial 1.0.0，直接 fork 会把整个仓库绑死在"禁止商用"上，以后想换许可也换不回来；另外换皮仓库有舆论风险。

**否掉**：fork 后改名（许可继承，限制传导）；复制部分文件（同样是衍生作品）。

**代价**：CDP 交互、限速这些轮子要重写一遍。可接受——它们不是这个项目的主要复杂度。

## D2 V1 只做只读免费层

**决定**：不实现任何发送与付费请求。

**为什么**：招聘端的付费点比预期更靠前——主动"索要附件简历"本身就是付费请求（平台前端里 `{1:"附件简历",2:"牛人意向",3:"电话号码",4:"微信号码",5:"面试邀请"}` 是同一组计费动作）。任何一次"向外伸手"都要花钱，且不可撤销。

**结果**：整个 V1 没有任何预算护栏需求，风险从"操作"降为"读取"。

## D3 在线简历是初筛，附件简历是复筛

**决定**：打分只基于在线简历；附件简历留给人确认后再去平台索要。

**为什么**：在线简历免费可读且结构化；附件简历在"主动路线"上要付费，在"投递路线"上由候选人自带。把两者混在一个流程里会让成本模型失真。

## D4 选择器外置

**决定**：所有 DOM 选择器写在 `config/selectors.boss.json`，代码只读配置。

**为什么**：开发时拿不到招聘端账号，无法校准；平台改版是常态。配置化至少让"改版"变成"改一行 JSON"，而不是"改代码再发版"。

**配套**：`bosscreen doctor` 做能力自检，字段缺失时明确报错，不用空值凑分。

## D5 "未知" ≠ "不满足"

**决定**：候选人字段缺失时记为 `unknown`，硬性条件按"待确认"处理，不计入失配。

**为什么**：默认"缺失=不满足"会静默误杀候选人，而且错得没有痕迹；"未知"会显示在名单里，人能一眼看到。

## D6 打分 = 硬条件 + 加权软分 + 理由

**决定**：两段式。先过硬条件（必须满足，可标"待确认"），再算加权软分并生成命中/缺失清单。

**为什么**：老板的真实需求通常是"几条硬门槛 + 一堆偏好"。纯 LLM 打分不可解释、不稳定；纯规则又太死。两段式既能解释，又能调。

**否掉**：纯 LLM 端到端排序（不可复现、贵、难调）。

## D7 Python + 标准库优先

**决定**：核心链路只用标准库（sqlite3、tomllib、json、dataclasses）。采集器可选依赖 httpx。

**为什么**：这是个要长期放在本地跑的小工具，依赖越少越不容易烂。也让"clone 下来就能跑 demo"成立。

## D8 MIT 许可

**决定**：MIT。

**为什么**：与"重写"配套；限制少、可被引用。合规与风险由 README 的声明承担，而不是靠许可证。

## D9 自研最小 CDP 客户端，不复用 BossHunter 的 3456 代理

**决定**：`cdp.py` 用标准库手写 WebSocket（握手 + 掩码帧 + ping/pong），直接连 Chrome 的 `webSocketDebuggerUrl`。`transport.py` 只做 HTTP 侧（`/json/version`、`/json/list`、`/json/new`、`/json/close`）。

**为什么**：BossHunter 的 Node 代理是它自己的运行时，依赖它等于把两套工具绑死；而 CDP 只需要一个很薄的客户端。代价是约 200 行协议代码，换来的是零外部依赖、可单独验证（headless Chrome 上 `1+1`、`navigator.userAgent`、DOM 读取都已实测通过）。

**边界**：只支持 `ws://` + 文本帧；不处理压缩扩展与二进制帧。够用就行。

## D10 未知一律计入分母，且筛选不隐藏未知

**决定**：`total = 100 * hit_w / total_w`（`total_w` 含未知项权重），同时给出 `coverage = judged_w / total_w`。看板的城市/学历筛选只排除"明确不符合"的人，未知值仍然显示。

**为什么**：第一版把未知从分母剔除，导致缺学历缺薪资的候选人拿满分并列第一——在一个筛选工具里这是致命的（资料越少分越高）。修法不是把未知当不满足（那会误杀），而是：不给分、但占分母、并显式标注"待确认/完整度"。

## D11 采集层用"样例页面"验收，真机校准留成配置动作

**决定**：采集逻辑（`collector.py`）不针对真实 BOSS 页面写死任何东西；用 `tests/fixtures/`
里的三份样例页面（同样的 container/item/fields 结构）验证整条链路。真实选择器放在
`config/selectors.boss.example.json`，未校准前 `calibrated=false`，`collect` 直接拒绝执行。

**为什么**：开发环境没有招聘端账号，真机无法验证。此时只有两条路——
(a) 照着猜测的类名写死采集逻辑，产出"看起来对"的脏数据；
(b) 把不确定的部分隔离成配置，用结构相同的样例页面证明"管线是通的"，把不确定性压缩到"选择器值"这一层。

选 (b)。它让"有账号之后要做什么"变成一件小事：填选择器、改一个标志位。
`calibrated` 闸门的作用是防止把猜测值带上真机——猜错会被当成"这个字段就是这样"，
比直接失败更危险。

**代价**：样例页面是我自己造的，它证明"管线通"，不证明"选择器对"。这一点在 state.md 里写明。

## D12 需求在看板上编辑，落库为准、文件回写为辅，存不上要显示

**决定**：`/api/requirement` 接一份 `spec`，`prepare_spec` 校验 → 重新打分 → 回写 SQLite（`requirements` + `scores`），
并把用户的 `--requirement` 文件也同步（父目录叫 `mock` 的样例文件不动）。落库失败不吞掉，
而是在响应里返回 `saved:{ok:false,error}`，弹窗里照实显示"已重新打分，但没存进库"。

**为什么**：需求写在 JSON 里，对目标用户（自己招人的老板）等于不可用——他不会去改 JSON。
但改需求是"评分口径"的变更，不能只在内存里生效、关掉页面就丢；也不能存失败还让人以为存上了
（下次打开是旧需求，人是被这个坑过的）。

**取舍**：没有做"撤销/多份需求方案"。V1 只保留一份当前需求——多方案是 V2 的事，
先把"能改、改完立刻看到结果、确实存住了"这三件事做对。

## D13 滚动翻页按"连续 3 次没有新卡片"判到底，而不是翻页参数

**决定**：`paging.mode=scroll` 时，Python 侧循环：滚动容器到底 → 等一拍 → 重新抽一次列表 → 按 href 合并去重；
连续 `stall_limit`（默认 3）次没有新卡片才认定到底，最多 `max_scrolls` 次。

**为什么**：
- BOSS 的列表页不认 `page=N`（个人端已实证），翻页只能靠滚动触发懒加载；
- 一次没长不代表没了——样例页就出现"滚一次、长一批、下一次不长"的交替节奏（懒加载 + 事件节流）。
  按"连续 2 次不长"判到底会误判成只有 5 条，所以放宽到 3 次并写进配置；
- 滚动 + 抽取放在 Python 侧循环，比写一段长 JS 好排错：每一步都能看日志、能过风控检查、能中途停。

**代价**：每次滚动都要重新抽一遍整页（`querySelectorAll` 全量），列表很长时是 O(n²)。V1 可接受——
一屏 20 条、滚 10 次也只有 200 次节点查询。

## D14 选择器体检做成独立命令 `check`，而不是塞进 `doctor`

**决定**：`doctor` 只做环境自检（Python 版本、配置、浏览器在不在、有没有 BOSS 页面）；`check --page` 才逐字段核对命中。

**为什么**：
- 两者触发条件不同：`doctor` 随时能跑、不联网；`check` 必须给一个真实页面 URL，跑一次就消耗一次页面预算；
- 一个命令做一件事，"哪一项错了"才说得清：容器错退出 3、字段错退出 1，脚本里能直接判断；
- 埋进 `doctor` 会让"环境没问题"和"选择器没问题"混成一个结论，恰恰是这两件事最容易互相掩盖。

**代价**：两条命令要分别记。README 与 state.md 里写成"有账号后的第一天"一条线，减少记忆负担。

## D15 需求方案以需求名为主键，改名即另存、同名即覆盖

老板说的是"我这个岗位的筛法"，不是一个无名字的配置项。所以方案的身份就是它的名字：
`save_requirement(id=name, ...)` 是 upsert，改名 = 多出一份，同名 = 改这一份。
切换方案走 `load_scheme` 只读重算，**不触发 `on_save`**——切着看看不该改动库。

代价：两份方案重名会互相覆盖。可以接受，因为看板上名字是用户自己看的，重名本来就会混淆。

## D16 导出用 CSV + UTF-8 BOM，未知字段留空

目标用户下一步动作就是"把这批人发给同事/自己排面试"，CSV 是最不需要解释的格式。
BOM 是因为国内用户十有八九用 Excel 双击打开，无 BOM 会把中文显示成乱码——
一个"导出成功但打开是乱码"的功能，等于没导出。

未知字段留空而不是填 0 或"无"：导出表会被当成事实转述。0 年经验和不填是两件事。

## D17 条件的中文名由系统生成，不让用户填

`skills contains_any ["Python"]` 出现在理由里，等于没写理由。看板编辑的需求没有 label，
所以在 `prepare_spec` 里按字段+操作+值生成一句人话（"会 Python 或 Go"、"学历 本科 及以上"）。
用户显式写了 label 就用用户的（`requirement.json` 里的手写文案优先）。

为什么不要求用户填 label：那是给系统看的字段，不该让人学。
